# مدل امنیت و احراز اصالت/مجوز (Security & Authorization)

## ماتریس تصمیم مجوز (Policy Evaluation)
هر تصمیم مجوز (AuthZ) حاصل رابطه زیر است:
`Decision = evaluate(Role, Action, TargetEntity, Scope(Province/Case), CurrentState, Delegation)`

## اصول امنیتی
- **نشست‌های امن (Secure Sessions):** کوکی‌های `HttpOnly` و `SameSite=Lax/Strict` همراه با محافظت CSRF.
- **تأیید دوعاملی (MFA):** فعال برای تمام نقش‌های مدیریتی (مدیر استانی، علمی، پیگیری، مدیر کل).
- **لغو بلادرنگ دسترسی:** تعلیق کاربر فوراً نشست و دسترسی‌های وب‌سوکت را باطل می‌کند.
- **فایل‌های ایمن:** آپلود فقط با شناسه یکتای تصادفی، اسکن ضدبدافزار، و دسترسی با لینک‌های امضاشده کوتاه‌عمر.

## پیاده‌سازی نشست وب (AT-31)
- نشست ورود در کوکی `tstaff_session` با ویژگی‌های `HttpOnly`, `SameSite=Lax` و در production با `Secure` نگه‌داری می‌شود؛ توکن نشست در پاسخ JSON یا `localStorage` قرار نمی‌گیرد.
- کوکی `tstaff_csrf` برای کد مرورگر قابل خواندن است و باید در `X-CSRF-Token` درخواست‌های تغییردهنده بازتاب داده شود؛ کوکی نشست همچنان `HttpOnly` است. CORS با `credentials` فقط برای مبدأهای مجاز فعال است.
- نقش‌ها از روابط سیستمی حساب استخراج می‌شوند؛ نقش‌های پژوهشی `MAIN_SUPERVISOR` و `COLLABORATOR_SUPERVISOR` نقش پنل نیستند. گارد API همچنان نشست و قلمرو منبع را در سرور بررسی می‌کند.
- ورود سریع برای کاربران ساختگی فقط وقتی `VITE_LOCAL_TEST_LOGIN=true` در محیط توسعه‌ی Vite و روی میزبان loopback فعال است نمایش داده می‌شود؛ دکمه‌ها از API عادی ورود استفاده می‌کنند. گذرواژه و فهرست حساب‌ها فقط در `apps/web/.env.local` قرار می‌گیرند و در build تولیدی حضور ندارند.
- برای توسعه محلی، سرویس ClamAV در `infra/compose/compose.dev.yml` ارائه شده است؛ API از `CLAMAV_HOST`, `CLAMAV_PORT` و `FILE_MAX_BYTES` استفاده می‌کند. فایل قرنطینه‌شده تا اسکن موفق قابل پیوست یا دانلود نیست.
